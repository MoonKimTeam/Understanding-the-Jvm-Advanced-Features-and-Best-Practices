# ch13. 스레드 안전성과 락 최적화

객체 지향 프로그래밍은 개발 효율을 높이고 규모가 훨씬 큰 소프트웨어를 구축할 수 있는 길을 엶
but, 현실 세계와는 다름

- 현실세계의 객체가 작업 도중 인터럽트되어 다른 객체로 전환되는 일이 반복
- 작업이 잠시 중단된 상태에서 객체 속성(데이터)이 바뀌어 이전 값이 의미가 없어지기도 함

## 스레드 안전성

- 정의

```text
- 특별한 스레드 스케줄링이나 대체 실행수단 고려 필요 없을 것
- 추가적인 동기화 수단이나 호출자 측에서 조율이 필요 없음
```

- 간단하지만 구현하기는 어려움 -> 많은 경우, 객체 호출 행위를 단일 호출로 제한하고도 스레드 안전하다고 함

### 자바 언어의 스레드 안전성

- 스레드가 안전한 정도에 따라 여섯 단계로 구분

#### 불변

- 불변 객체가 올바르게 만들어진다면, 외부에 보이는 상태는 절대 달라지지 않고 멀티 스레드 환경에서도 일관성 보장
- 자바에서 기본 데이터 타입은 final로 정의 시 불변이고, 객체의 경우는 메서드가 필드를 수정하지 않도록 해야 함
- 아직 값 타입 지원 안 함
- `Long`, `Double`, `Integer`와 `BigInteger` 등 `java.lang.Number`의 대부분의 하위 클래스들은 불변
- `AtomicInteger`, `AtomicLong`은 불변 아님

#### 절대적 스레드 안전

- 자바 API에서 스레드 안전하다고 표시된 클래스 대부분이 절대적 스레드 안전을 의미하지 않음
- `java.util.Vector`는 모든 메서드가 synchronized 메서드이므로 스레드 안전
    - 그렇다고 해도 호출자가 추가로 동기화할 필요 없다는 것은 아님
        - `Vector`에 스레드 안전하게 접근하려면 추가 조치 필요함(synchronized 감싸기)

#### 조건부 스레드 안전

- 일반적으로 우리가 '스레드 안전하다고 말할 때'의 수준
- 단일한 작업을 별도 보호 조치 없이 안전하게 수행
- but, 특정 순서로 연달아 호출 시 추가 동기화 필요
- `Vector`, `HashTable`, `Collections` 클래스의 synchronized 메서드들

#### 스레드 호환

- 스레드로부터 안전하지 않지만 호출자가 적절히 조치하면 멀티 스레드 환경에서도 안전 사용 가능
- 자바 대다수 클래스. `ArrayList`, `HashMap` 등

#### 스레드 적대적

- 호출자가 동기화 조치를 취하더라도 멀티 스레드 환경에서 안전 사용 불가
- `Thread` 클래스의 `suspend()`, `resume()` 메서드 -> 동시 실행 시 교착 상태 됨. deprecated 대상임

### 스레드 안전성 구현

#### 상호 배제 동기화

- 가장 일반적이면가 가장 중요
- 동기화란 공유 데이터에 여러 스레드가 접근하려는 상황에서 그 어떤 시점에든 단 하나의 스레드(세마포어는 여러 개 가능)만을 사용할 수 있다는 뜻
- 뮤텍스, 임계 영역, 세마포어
- synchronized 키워드
    - synchronized 키워드(컴파일하면 동기화 블록 전후에 monitorenter, monitorexit 바이트 명령어 생성됨)
        - monitorenter 실행 시 현재 스레드가 락 소유 시 락 카운터 값 1 증가, monitorexit 실행 시 1 감소
    - synchronized 키워드는 매우 주의해서 사용 필요
        - 같은 스레드라면 synchronized로 동기화된 블록에 접근 가능
        - 락 소유 스레드가 작업 마치고 락 해제 할 때까지 다른 스레드 진입 차단
    - 락 소유는 실행 비용 측면에서 무거움
        - JVM은 플랫폼 스레드를 운영 체제와 매핑하고 이는 운영체제의 사용자 모드와 커널 모드 전환이 불가피 하다는 뜻
        - 특히, 게터 세터 같이 간단한 코드에 설정하면 모드 전환에 아주 긴 시간 소요 -> 제한적으로 사용해야
    - cf)자바는 스레드 블록 전 운영체제에 바쁜 대기 코드를 추가해서 모드 전환이 자주 발생하지 않도록 하기도 함
- `java.util.concurrent.locks.Lock` 인터페이스가 새로운 상호 배제 동기화 제공
    - 논블록 구조 등 다양한락으로 확장 가능
    - `ReentrantLock`(대기 중 인터럽트, 페어락, 둘 이상의 조건 지정 등 진보된 기능)
    - synchronized는 멀티스레드 환경에서 성능이 급격히 떨어지지만, `ReentrantLock`은 안정적 -> JDK 6 이후엔 syncrhonized도 개선
    - 그럼에도 synchronized가 나은 점
        - synchronized는 매우 명확하고 간결하므로, 이 쪽이 익숙하고 기본 동기화 기능만으로도 충분한 경우 사용
        - `Lock`은 finally에서 해제 필요
        - 성능 차이는 예전 얘기이고, `Lock`을 이용하면 JVM은 어느 스레드가 어느 락 소유하고 있는지 모름

#### 논블로킹 동기화

- 상호 배제 동기화 시 스레드일시 정지와 깨우기가 성능을 저하시킴(블로킹 동기화)
- 상호 배제 동기화는 비관적 동시성 전략
- 하드웨어 명령어집합이 발전하면서 다른 선택지 -> 낙관적 동시성 전략
    - 잠재적으로 위험하더라도 일단 작업 진행
    - 경합하는 다른 스레드 없으면 성공, 충돌 시 보완조치(계속 재시도 등)
    - 스레드를 일시 정지할 일이 없으므로 논블로킹 동기화라고 함
    - 이런 코딩 방식을 락프리 프로그래밍
- 낙관적 동시성 전략에 하드웨어 명령 집합의 발전이 필요했던 이유: 작업진행, 충돌감지를 한 명령어처럼 원자적 수행 필요
    - 하드웨어는 의미상하나이나 여러 연산으로 처리해야 하는 특정 작업을 단 하나의 프로세서 명령어로 완료되게끔 보장 가능
    - 여러 가지 명령어를 통해서 가능해짐(TAS, FAA,...)

#### 동기화 필요 없는 메커니즘

- 아무런 장치(동기화)의 도움 없이도 스레드 안전성 보장할 수 있는 경우 있음(공유 데이터 없는 경우 처럼)
    - 재진입 코드(순수 코드): 실행중간에 아무 때나 끼어들어 다른 코드를 수행하고 와도(재귀 호출 포함) 상관 없는 코드
        - 전역 변수, 힙에 저장된 데이터, 공유 시스템 자원을 전혀 사용하지 않고 필요한 모든 정보를 매개 변수로 받음
        - 메서드의 반환값이 예측 가능, 똑같은 입력에 똑같은 결과 반환 -> 재진입 가능, 스레드 안전
    - 스레드 로컬 저장소
        - 코드 조각에서 사용하는 데이터를 다른 코드와 공유해야 한다면, 데이터를 공유하는 다른 코드와 같은 스레드에서 수행된다고 보장되는지 확인
            - 동기화 필요 없음
        - 요청 하나당 서버 스레드 하나를 배정하는 웹서버에서 스레드 로컬 저장소를 이용해 스레드 안전성 문제 해결 가능

## 락 최적화

### 스핀 락과 적응형 스핀

- 멀티코어 시스템에서는 대기상태로 들어가지 않고도 원하는 락이 해제되는지 옆 코어에서 지켜볼 수 있음
    - 스레드를 멈추지 않고 루프를 돌리면(spin) 가능
- JDK 6부터 기본 활성화
- 락이 잠깐이면 효과 좋지만, 길어지면 루프만 돌면서 자원 낭비
    - 스핀락 대기 시간 제한 후 기존 처럼 스레드 일시정지
- 스핀 시간이 고정 안 되고 락의 이전 스핀 시간과 락의 소유자 상태에 따라 결정되는 `적응형 스핀` 도입됨

### 락 제거

- 특정 코드 조각에서 런타임에 데이터 경합이 일어나지 않는다고 판단되면 JIT 컴파일러가 해당 락 제거하는 최적화 기법
    - 실제 자바 프로그램에는 개발자가 추가하지 않아도 동기화 장치가 많이 쓰이고 있음
    - `StringBuffer.append()` 등

### 락 범위 확장

- 연이은 다수의 작업이나 순환문에서 똑같은 락 객체를 반복해서 잠그고 해제하는 상황
    - 똑같은 락 객체를 잠그는 일련의 단편적인 작업들을 발견하면 락의 유효범위를 해당 작업 전체로 늘림

### 경량 락

- 스레드 경합을 없애 뮤텍스를 사용하는 기존 중량 락의 성능 저하를 줄임

### 편향 락

- 경합이 없을 때 데이터 동기화 장치들을 제거하여 프로그램 실행 성능을 높이는 최적화 기법
